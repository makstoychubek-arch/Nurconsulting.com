## 1. Что сломалось и что сделали

Пустой `items` был из двух дыр сразу:

1. Тело `{ items: [{ id }] }` — WB отвечает 200 и `items: []`. Нужно `{ items: [{ advertId, nmId }] }`.
2. Даже с верным телом старый обход искал поля `normquery` / `phrase` и **не читал** `normQueries.active` (массив строк). Кластеры бы не сохранились.

Сделано:

- общее тело `listClustersBody` / разбор `parseListClustersResponse`
- пары по **всем** `nm_settings`, пачки по 100
- статус больше не режет (нужны и завершённые, в т.ч. 38634350)
- кабинеты по очереди, upsert кластеров одной пачкой (первый прогон упёрся в 150 с)

`get-bids` в тике уже был верный (`advert_id` / `nm_id`). Сведён к тому же хелперу `getBidsBody`.

## 4. Сквозной прогон на 38634350 — согласен, с оговорками

План: tick → `bid_history` на завершённой **38634350**, кластеры `пиджак для женщин` / `пиджак женский коричневый`, **DRY_RUN**. Правило **не вставлял** (`autobidder_rules` = 0).

**Согласен.** Это сейчас единственная manual+CPM в фокусе, у которой `get-bids` реально отдаёт ставки. Живые СРС тик не двинет (setBids только CPM). Кампания закрыта — случайно поднять ставку в аукционе не на чем.

Риски, не стоп-факторы:

1. Тик **не смотрит status**. Если кто-то снимет `DRY_RUN` (секрет или `"dry_run": false`), уйдёт `setBids` на завершённую РК. WB скорее ответит ошибкой, но это уже запись в рекламный API. Пока секрет `DRY_RUN=true`, тело cron `{}` → dry-run.
2. Cron `*/5` будет писать `bid_history` + снапшоты, пока правило `is_active`. После прогона — выключить SQL из `docs/autobidder-trial-rule.md`.
3. Без `positions` в теле будет `pos_unknown` и желание поднять 420 → ~450 KGS, `applied=false`. Чтобы увидеть `pos_worse`, в вызов: `"positions": { "пиджак для женщин": 15 }`.
4. `max_bid` в SQL — **500** (KGS), не 80 «рублей».
5. Не ставить `status='active'` у этой строки в `adv_campaigns`.

SQL готово: `docs/autobidder-trial-rule.md` (один кластер; второй можно добавить тем же insert). Жду «вставляй» — сам не выполняю.
